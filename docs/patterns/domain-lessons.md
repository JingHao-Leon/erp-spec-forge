# 领域结构模式：从真实系统蒸馏

> 来源声明：本文模式提炼自对**两套真实生产系统**（一套传统单体 ERP 与一套主流生鲜供应链 SaaS）的授权安全评估/逆向分析，全部经过匿名化与泛化处理——不含任何真实系统名称、地址、凭据或业务数据。每条模式都标注了它在 erp-spec-forge 中的落点。

## 1. 模块注册表即演进史

**观察**：两套系统都维护一张"模块/功能注册表"（150+ 项），顶级模块用数字段编号（如 1xx 基础、2xx 采购、5xx 商城、9xx 设置），编号段之间的空隙与新增模块号直接暴露了系统的功能演进顺序。注册表 + 功能码两级结构支撑了细粒度授权。

**落点**：`specs/rbac.yaml` 的 `modules` + 实体 CRUD 功能码自动推导；`generate --out dist` 产出的 `registry.json` 就是这张注册表的规范化形态，可直接喂给前端菜单与权限中间件。

## 2. 主数据"锁定三件套"

**观察**：真实系统里几乎所有主数据（供应商/客户/采购员/承运商/司机/仓库……）都重复手写同三个字段：`status`(normal/locked) + `lock_operator`(谁禁的) + `lock_time`(何时禁的)。手写导致口径漂移：有的叫 stopped、有的叫 disabled、有的漏掉操作人。

**落点**：实体级开关 `lockable: true`——加载时自动注入标准三件套，已手写的同名字段不覆盖。禁用语义全系统统一。

```yaml
- name: supplier
  display: 供应商
  lockable: true
  fields: [...]
```

## 3. 单据审计三件套

**观察**：交易单据普遍需要 `created_at`/`created_by`/`updated_at`，但手写覆盖率参差——有的单据有创建时间没创建人，有的全无。

**落点**：实体级开关 `auditable: true`——按需补齐缺失的审计字段，已有字段不重复注入。

## 4. 生效日期驱动的比例分配

**观察**：生鲜采购中"一个商品由多个供应商按比例供货，且比例按配送日期生效"（今天 7:3、明天换 5:5），实现为「商品×供应商×生效日期」的分配表，历史比例保留可溯。

**落点**：示例规格 `goods_supply_ratio`（goods × supplier × delivery_date × ratio）。

## 5. 双轨系统的"同步键"

**观察**：某真实部署中新旧两套系统并行（新 SaaS 跑核心交易、老系统跑溯源/监控等外围），靠每个客户/供应商身上的"外部平台编号"字段互相缝合，并周期性从一侧拉取清单同步到另一侧。同步键缺失或不一致是这类架构最高频的事故源。

**落点**：`customer.external_code` / `supplier.external_code` 字段进入示例规格；同步接口（清单拉取、批量导入）在生成的 OpenAPI 中对应 `GET /customers`（分页 + keyword）与 `POST /customers`。

## 6. 单据状态机的"发布/回收"对称

**观察**：采购任务类单据普遍存在「草稿 → 已发布 → 执行中 → 完成」主干，且**发布操作可逆**（回收回草稿）——这是把"对下游可见性"做成显式状态的典型设计；取消通常只能从发布前状态发起。

**落点**：`specs/workflows/purchase_task.yaml`；校验器强制初始态可达、非终态有出边，防止规格里出现"死状态"。

## 7. 溯源合规域

**观察**：食品供应链的合规需求固化为：批次号（入库时挂）→ 检测报告（挂批次，含图片与检测项）→ 面向公众的扫码页（可配置展示客户/数量/流转时间）。

**落点**：示例规格 traceability 领域（trace_batch / inspect_report / trace_setting）。

## 8. 冷链 GPS 监控域

**观察**：车辆监控固化为「设备注册 → 路线×客户×司机×车辆×设备 排班绑定 → 五类报警（偏航/温度/迟到/禁入/禁出）→ 送达时间与里程记录」。

**落点**：示例规格 delivery 领域（gps_device / gps_alarm / route_bind / delivery_record）。

---

以上模式的共同点：它们在两套**技术栈完全不同**的系统里以几乎相同的形态出现——说明它们是领域约束而非实现巧合，值得作为规格层的默认约定。
